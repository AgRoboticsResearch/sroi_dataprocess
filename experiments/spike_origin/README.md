# 夹爪尖峰是从哪来的？（2026-10-24）

> 这份报告把"夹爪尖峰"这个问题的完整过程记录下来：怎么发现、怎么归因、
> 现在的方案为什么不再出尖峰、序列层去尖峰代码为什么退役。也可以直接作为
> 汇报素材。
>
> 复现命令：`python3 experiments/spike_origin/scan_narrowband_spikes.py all`
> （全集扫描，约 55 分钟；只跑嫌疑名单用 `suspects`）。

## 命名口径（与用户统一）

- **v1 方案** = 窄带全行检测：只在图像第 395–450 行的全宽条带里找两个 tag，双对角线
  41±9 px，**每 ID 取检出顺序里的最后一个**。2026-07-09 钳口改造（commit `f4c8162`）
  后启用，一直用到 10-14。**近 3 个月的处理结果和训练模型都基于 v1。**
  （更早的 200 行全宽版不做讨论，一切从 v1 说起。）
- **v3 方案** = 现行完全形态（本仓库当前管线，onesb_v3 数据集）。其最早形态
  （10-14）就引入了新的 ROI 区域（左右窗条）与多重判据，之后逐步完善。

## 事件线

1. **做数据清洗的时候发现尖峰。** 不少 episode 的夹爪开度曲线上有孤立的 1–2 帧
   怪值——前后都平滑，就中间蹦出一个离谱值。当时不知道成因，只能针对尖峰本身
   做处理：设计了一个"平坦上下文去尖峰"器（前后各 3 个有效样本的包络外
   0.15×量程、≤2 帧才算尖峰），见一个删一个，再把洞插回去。
2. **后来 tag 检测引入了新的 ROI 区域和一些判据。** 检出之后仍然保留集中去尖峰
   的处理，但发现尖峰其实已经没有了——说明**尖峰在检测 tag 的环节就已经被杀死
   出现的可能性**，程序里保留的去尖峰处理也就没用了。
3. **本报告把病根查实。** 用 v1 方案逐行复刻检测函数，历史尖峰帧号逐一命中、
   数值量化吻合；再对全集 1138 条扫描，得到 v1 时代全部尖峰：**21 集（1.8%）、
   共 22 帧**。所以序列层的去尖峰处理应该从管线中退场——它在检测层根治后
   永远没有触发机会。

## 病根：一句话版本

v1 在整条 55 像素高的横带里找 tag，且**每个 ID 只认检出顺序里的最后一个**。只要
画面里别处（设备箱、地面阴影、钳口高光……）凑出一个同 ID、尺寸也合格的四边形，
而且它在检出顺序里排在真 tag 后面，**假货就把真货覆盖了**，距离值瞬间离谱——
这就是尖峰。检出顺序由图像内容决定，完全可重复（无随机性），但没有任何正确性
保证，所以尖峰"偶发、孤立、看起来随机"。

## 尖峰全集与注释图

全集扫描结果在 `narrowband_spike_scan.csv`（21 集 22 帧，每帧含误检两侧的坐标
与对角线）。22 张尖峰帧注释图在 `frames_narrowband/`：带外压暗，黄线 = v1 的
搜索带边界；框 = 该帧实际配对出距离的两个检出，含 ID 与对角线标注。被假货
挤掉的真 tag 不带框。对汇报而言，翻这几张图就能直观看到：**误检的四边形藏在
画面什么位置、它是怎么顶替真 tag 的。**

## 为什么现在的管线不再出尖峰

按"误检测是否落在当前 ROI 区域内"分两种情况：

- **落在 ROI 窗条之外**：v3 的左右窗条把每个 ID 的搜索范围限制到"物理上只可能
  存在一枚正确 tag"的窄条，这类误检**结构性消失**——画面别处的假货根本不进入
  检测。
- **落在 ROI 窗条之内**：仍然可能。真 tag 旁边的高光、反光可能凑出退化四边形
  （对角线尺寸还能凑进 41±9），它会影响钳口开度的估计。这类误检由**解码质量
  闸**（`hamming == 0`，已实装，作用于预处理链的每一级——某级被拒不终止，升级
  重检直到三级全失败才算缺检）保证被舍弃。全集验证（1138 集、208,887 个带内
  检出）：窗内尺寸合格检出 99.64% ham==0；代价仅 704 条（0.36%）转缺检，交给
  对称补全和插值吸收；而尺寸合格却落在窗外的尖峰源头候选 301 条里 300 条
  ham≥1、全部被闸+窗条消灭。曾考虑的第二道闸 `decision_margin ≥ 30` 经全集
  验证放弃——对 22 个已知假 tag 与 ham 闸完全重复，却会多杀 943 个真检出。

一句话：**病根在检测层。ROI 外的误检已结构性排除，ROI 内的误检交给置信度闸；
序列层的去尖峰处理从此永远没有触发机会，注释退役。**

## 处置

- `gripper_tag_core.py::finalize_series` 里的 `remove_spikes` 调用已**注释退役**
  （函数定义保留备查；v3 stats schema 起不再输出 `spikes_removed` 键，无下游依赖）。
- 解码质量闸已实装：`detect_window_strip` 的每级候选须 `hamming == 0`（常数
  `DECODING_HAMMING_MAX`）；闸参数记录在 `gripper_normalization.json` 的
  `processing.decoding_quality_gate`；stats 也按 v3 schema 重建（字段自带
  `field_docs` 说明）。
